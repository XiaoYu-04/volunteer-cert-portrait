## 1. 并发占名额无锁化 —— 一条 SQL 消灭 TOCTOU

**问题**
「活动名额已满就拒绝报名」如果写成「先 `SELECT` 查已报名数 → 再 `INSERT`」，
两个并发请求会**同时**读到「还差 1 个名额」，然后**都**插入成功 —— 这就是经典的
TOCTOU（Time-of-Check to Time-of-Use）竞态。常规解法是加行锁或乐观锁版本号。

**方案**
不加锁、不加 `version` 列，改成**把判断和写入压进同一条 `UPDATE`**，
用数据库自身的行锁保证原子性，**影响行数为 0 就是「已满」**：

```sql
-- volunteer-cert-portrait-server/vcp-volunteer/src/main/java/com/vcp/volunteer/mapper/VolunteerActivityMapper.java:35-36
UPDATE volunteer_activity SET signed_count = signed_count + 1, update_time = NOW()
 WHERE id = #{id} AND deleted = 0 AND (max_count <= 0 OR signed_count < max_count)
```

`(max_count <= 0 OR ...)` 这一段是**刻意加的**：`max_count = 0` 表示「不限名额」，
若只写 `signed_count < max_count`，不限名额的活动会**永远报满**。
Mapper 的注释里把这一点写明了（`VolunteerActivityMapper.java:30`）。

释放名额走对称的一条（`GREATEST` 兜底，防止计数被减成负数）：
`VolunteerActivityMapper.java:48`。

## 2. 时长口径 A1 —— 异常回退 + 1.5 倍封顶

**问题**
服务时长是**全系统的结算依据**（画像等级、学院排行、看板合计都从它来），
但现实里会出现两类脏数据：① 学生签到了没签退；② 签到状态被标为异常。
如果一律按 0 计，学生白干；如果一律按「签退 − 签到」算，没签退就算不出来。

**方案**
三级回退 + 一道封顶，全部集中在**一个纯函数**里：

| 情况 | 取什么值 |
|---|---|
| `NOT_SIGNED` / `ABSENT` | **0.00** |
| `SIGNED_OUT` 且有完整签退时间 | `(签退 − 签到) / 3600`，保留 2 位小数 |
| 缺签退、或状态 `ABNORMAL` | 回退到**活动预计时长** |
| 活动预计时长为空或 0 | 不封顶，直接用实际值 |
| **最终封顶** | 不超过活动预计时长的 **1.5 倍** |

封顶那两行是核心：

```java
// volunteer-cert-portrait-server/vcp-volunteer/src/main/java/com/vcp/volunteer/support/AttendancePolicy.java:137-139
BigDecimal cap = planned.multiply(VolunteerConstants.HOURS_CAP_RATIO)
        .setScale(VolunteerConstants.HOURS_SCALE, RoundingMode.HALF_UP);
return actual.min(cap);
```

**为什么是 1.5 倍**：签到窗口开放到「活动结束后 30 分钟」，
若不封顶，学生可以在窗口内一直挂着刷时长；1.5 倍既容得下合理的超时服务，
又堵住了「签到窗口被滥用」这条路。理由原文写在 `docs/待办清单.md:195`。

**证据**

| 项 | 出处 |
|---|---|
| 决策原文（A1） | `docs/待办清单.md:192`~`:195` |
| 常量集中定义 | `.../vcp-volunteer/.../constant/VolunteerConstants.java:25`~`:26`（`HOURS_CAP_RATIO = new BigDecimal("1.5")`） |
| 封顶与回退实现 | `.../support/AttendancePolicy.java:121`~`:140`（`resolveHours`）、`:150`~`:160`（`actualHours`）、`:168`~`:173`（`normalizePlanned`） |

## 3. 签到窗口 A2 —— 惰性判定，不引入定时任务

**问题**
「活动结束后 30 分钟未签退记为缺勤」这个状态转换，最直觉的实现是**定时任务**
（每分钟扫一遍表把超时的改成 `ABSENT`）。但定时任务会带来：多实例部署要分布式锁、
任务挂了状态就永远不更新、上线要多配一个调度组件。

**方案**
**查询时惰性判定** —— 不落库、不定时，每次读签到记录时用当前时间算一遍真实状态：

```java
// .../vcp-volunteer/.../support/AttendancePolicy.java:85-93
public static boolean isSignInOpen(LocalDateTime activityStartTime, LocalDateTime activityEndTime, LocalDateTime now) {
    if (activityStartTime == null || now == null) { return false; }
    LocalDateTime openAt = activityStartTime.minusMinutes(VolunteerConstants.SIGN_IN_OPEN_MINUTES);
    LocalDateTime closeAt = effectiveEndTime(activityStartTime, activityEndTime)
            .plusMinutes(VolunteerConstants.SIGN_OUT_DEADLINE_MINUTES);
    return !now.isBefore(openAt) && !now.isAfter(closeAt);
}
```

窗口口径：**活动开始前 30 分钟开放签到**，**活动结束后 30 分钟内必须签退**。

一个容易漏的边界被显式处理了：库里允许 `end_time` 为空，
此时按**开始时间兜底**，使窗口退化为「开始前 30 分钟 ~ 开始后 30 分钟」，
而**不是**变成永久开放（`AttendancePolicy.java:175`~`:185` 的注释把这一点写明了）。

> ⚠️ **这个设计直接决定了演示时的一个现象**：演示数据里已发布的活动都在**未来**，
> 所以现场点「签到」会提示「活动开始前 30 分钟才可签到」—— **这是设计内行为，不是 bug**。
> 演示话术见 `docs/答辩材料/演示脚本.md` 的「降级方案」一节。
>
> ⚠️ **学生自助签到（B24，2026-09-26 新增）同理：真后端演示需先造一场窗口内活动。**
> `GET /api/v1/attendance/mine` 只按登录态取本人签到记录（学生的 5 条权限里没有签到项，
> 因此只挂 `@SaCheckLogin`、无权限码），学生端「我的报名」页据此渲染签到 / 签退按钮 ——
> 而按钮**只在服务端判定窗口已开时才出现**。演示库当前没有窗口覆盖此刻的活动，
> 全新重建的库里 `student` 也没有 `NOT_SIGNED` 签到记录，所以**按钮不会出现**：
> 要在真后端演示成功签到，需**先现场发布一场时间覆盖当前的活动**（开始时间设为当前时间前 10 分钟），
> 学生报名 → 组织审核通过（自动生成 `NOT_SIGNED` 记录）→ 再签到 / 签退（步骤见
> `docs/答辩材料/演示脚本.md` 第 2.4 步的 (a) 路径）。
> **纯前端 mock 口径**（`VITE_USE_MOCK=true`）**没有这个前置** —— mock 刻意不做 30 分钟窗口校验，点签到一定能过。

## 4. 驳回重提 A4 —— 清空状态但保留审核轨迹

**问题**
学校管理员驳回一条时长后，学生/组织要能改了再交。直觉做法是**更新同一行**，
把 `audit_user_id` / `audit_time` / `audit_remark` 清空。
但这会**抹掉驳回历史** —— 事后追责时看不出「这条被驳回过几次、谁驳的、为什么」。

**方案**
**两处同时写**：
① 更新 `service_duration`：状态回 `PENDING_AUDIT`，三个审核字段清空；
② **往 `duration_audit` 追加一条新的 `SUBMIT` 流水** —— 历史不覆盖。

```java
// .../vcp-certification/.../service/impl/DurationServiceImpl.java:191-202
target.setAuditUserId(null);
target.setAuditTime(null);
target.setAuditRemark(null);
...
recordSubmitFlow(target.getId(), activity.getTitle(), hours);   // 追加 SUBMIT 流水
```

于是「**驳回 → 重新提交 → 再审核**」这条链路的唯一凭据就是 `duration_audit` 表 ——
这也是它在 ER 图里被描述为「唯一凭据」的原因。

一个**命名上的坑**被显式区分开了：`duration_audit.action` 存的是**动词原形**
（`SUBMIT` / `APPROVE` / `REJECT`），而 `service_duration.status` 存的是
**过去分词/形容词**（`APPROVED` / `REJECTED`）—— **不同形**，别混。

## 5. `total_duration` 权威表 A5 —— 一份权威值 + 一份可重算快照

**问题**
库里有**两个** `total_duration`：`student_info.total_duration` 与
`student_profile.total_duration`。两者含义重复，一旦都能被写，迟早不一致 ——
而且这种不一致**不会报错**，只会让「我的时长」和「公益画像」两个页面显示不同数字。

**方案**
**A5 拍板：以 `student_info.total_duration` 为唯一权威值**，审核通过时由后端累加；
`student_profile` **仅作画像快照**，可随时由前者重算。
并且把这个口径**写进了自检脚本** —— 第 9 项专门检查「画像快照是否过期」：

```sql
-- sql/09_consistency_check.sql:168-169（第 9 项）
'student_profile.total_duration ≠ student_info.total_duration（画像快照过期）'
```

也就是说：**口径不只写在文档里，还被一条可执行的 SQL 钉住了**。
一旦哪次代码把快照写歪，自检立刻报非 0。

等级重算同样是「按权威值算、变了才写」：


## 6. 画像 6 档 8 类 —— 按 `code` 映射而非中文名

**问题**
「取参与次数最多的活动分类，映射为类型标签」这条规则，

同一份数据在不同机器上可能给出不同的并列打破结果，三人各自跑出来的画像会不一样。

## 7. 安全三件套 —— 密文、锁定、改密踢会话

**问题**（三件事，每件都是真实被发现的缺口）

1. 口令**明文入库**，且演示口令 `123456` 就写在文档里；
2. **零登录防护** —— 无验证码、无失败计数、无锁定（审计时全仓零命中）；
3. **没有「修改密码」能力** —— 前端页面上写着提示，后端没有接口。

**方案**

| # | 措施 | 实现 |
|---|---|---|
| ① | 口令 **BCrypt 单向哈希**入库，明文不落库 | `vcp-framework/.../util/PasswordUtils.java`；强度 10（`:24`）、密文前缀校验 `$2a/$2b/$2y`（`:39`）、固定 60 字符（`:42`）、编码器 `:49` |
| ② | 登录**连续 5 次失败锁 15 分钟** | `.../service/impl/LoginAttemptGuard.java:37`（`MAX_FAILURES = 5`）、`:40`（`LOCK_MINUTES = 15`）、`:110`~`:111`（达到阈值即置 `lockedUntil`） |
| ③ | **本人改密** `PUT /api/v1/auth/password` + **管理员重置** `PUT /api/v1/system/users/{id}/password` | `AuthServiceImpl.java:290`~`:307`（本人改密）、`UserServiceImpl.java:273`~`:282`（管理员重置） |

两个**刻意的顺序设计**，说明想过攻击面：

- **锁定判定必须排在查库与口令校验之前** —— 因为一次 BCrypt 约 50~100ms，
  若先校验口令再判锁定，等于给攻击者免费的计算资源：
  `AuthServiceImpl.java:113` 的注释原文即此意。
- **改密时先比对新旧口令是否相同，再走 BCrypt** —— 省掉一次 50~100ms 的哈希：
  `AuthServiceImpl.java:295` 注释原文。

还有一处**编码前先校验策略**的细节：超长明文喂给 Spring Security 的 BCrypt 编码器
会**直接抛 `IllegalArgumentException`**，所以必须先 `checkPolicy` 再 `encode`
（`UserServiceImpl.java:158`~`:162`、`PasswordUtils.java:33`~`:34`）。

## 8. 多模块依赖规则 —— 防止 11 个模块互相腐化

**问题**
后端拆成 **11 个 Maven 模块**。拆得越细，越容易出三种腐化：
① 模块间**循环依赖**；② 跨模块**直接访问对方 Mapper/表**（今天图快，明天改不动）；
③ 依赖版本**各处各写**。

**方案** —— 三条硬规则 + 一条踩坑固化：

**规则一：`vcp-dependencies` 作为独立 BOM，禁止继承聚合根。**
这不是风格问题 —— 声明了 `parent` 会与根 pom 的 `dependencyManagement` BOM 导入
**形成循环依赖，Maven 直接拒绝读取整个工程**。所以 pom 里留了注释防止后人「顺手补回去」：

```xml
<!-- volunteer-cert-portrait-server/vcp-dependencies/pom.xml:7-11 -->
<!--
  本模块为独立 BOM，刻意不继承聚合根 pom。
  若在此声明 parent 为 volunteer-cert-portrait-server，会与根 pom 的
  dependencyManagement 导入形成循环依赖，Maven 将直接拒绝读取整个工程。
-->
```

**规则二：跨模块只调用对方 Service 接口，禁止直接访问对方 Mapper/表。**
出处：`CLAUDE.md`「后端模块结构」的依赖规则段。

**规则三：通知类耦合用 Spring Event 解耦。**
操作日志是典型场景 —— 切面**只发事件**，不直接写 `operation_log` 表：

```java
// vcp-framework/.../log/OperationLogAspect.java:157
eventPublisher.publishEvent(new OperationLogEvent(this, userId, username, operation, ...));
```
```java
// vcp-system/.../event/OperationLogListener.java:41
@EventListener
```

于是 `vcp-framework`（切面所在模块）**不需要知道 `vcp-system` 的存在** ——
依赖方向保持单向。

**证据**

| 项 | 出处 |
|---|---|
| BOM 不继承聚合根（含原因注释） | `volunteer-cert-portrait-server/vcp-dependencies/pom.xml:7`~`:11` |
| 11 个模块划分 | `CLAUDE.md`「后端模块结构」 |
| 依赖规则原文 | `CLAUDE.md`「后端模块结构」末段（「禁止反向依赖与循环依赖；跨模块只调用对方 Service 接口，禁止直接访问对方 Mapper/表；通知类耦合用 Spring Event 解耦」） |
| Spring Event 发布侧 | `vcp-framework/.../log/OperationLogAspect.java:34`（注释「切面只调用 `publishEvent` 发布」）、`:157` |
| Spring Event 监听侧 | `vcp-system/.../event/OperationLogListener.java:41` |
| 构建验证 | `mvn -B package -DskipTests` → **11 个模块 BUILD SUCCESS**（`docs/答辩前待办.md:44`~`:46`，2026-09-25 重新打包） |

## 9. 活动图片上传 —— 元数据入库 + 文件落盘 + 路径穿越防护

**问题**
活动需要「1 张封面 + 最多 6 张带说明图片」。直接把图片二进制塞进 PostgreSQL 会
让库迅速膨胀、备份变慢；直接按用户传的文件名落盘又会踩**路径穿越**
（文件名传 `../../etc/passwd`）。

**方案**
**分工**：PostgreSQL 只存**附件元数据**（`attachment` 表），图片本体写入后端 `uploads/` 目录，
库里存 `/uploads/...` 形式的**相对地址**。前端通过静态资源映射访问。

关键的一段是**规范化后校验前缀**：

```java
// vcp-system/.../service/impl/AttachmentServiceImpl.java:76-84
Path target = root.resolve(relative).normalize();
if (!target.startsWith(root)) {
    ...   // 拒绝：解析后跑出了上传根目录
}
Files.createDirectories(target.getParent());
Files.copy(input, target, StandardCopyOption.REPLACE_EXISTING);
```

`normalize()` 把 `..` 折叠掉，再用 `startsWith(root)` 判断是否越界 ——
**先规范化、再比较**，顺序不能反。

**证据**

| 项 | 出处 |
|---|---|
| 接口 | `POST /api/v1/attachments/images` —— `vcp-system/.../controller/AttachmentController.java:36` |
| 上传实现 | `vcp-system/.../service/impl/AttachmentServiceImpl.java:59`（`uploadActivityImage`）、`:76`~`:84`（路径校验与落盘） |
| 目录与前缀配置 | `AttachmentServiceImpl.java:51`（`vcp.upload.dir:./uploads`）、`:55`（`vcp.upload.public-prefix:/uploads`） |
| 静态资源映射 | `vcp-framework/.../config/WebMvcConfig.java:39`、`:92`~`:109` |
| 表结构 | `attachment` 的 `content_type` / `caption` / `sort_order` —— `sql/02_schema.sql:220`~`:222`（`sql/11` 为老库幂等补列） |
| 用例 | `docs/测试用例表.md:145`~`:156` 共 **8 条**（TC-IMG-01~08），含「上传非图片或伪扩展名 → `10001`，不落盘」「上传超过 5MB → `10001`」「未登录或学生上传 → `20001`/`20003`」 |
| 已完成标注 | `docs/答辩前待办.md:20`（「活动图片上传已完成：封面 + 最多 6 张图文说明，PostgreSQL 存元数据、文件落盘」） |

> **如实说明**：`ORG`（组织资质材料）与 `AVATAR`（用户头像）两个业务类型的上传

## 10. 演示数据确定性算法 + 带断言的幂等自检

**问题**
三个人在各自机器上跑演示数据脚本，如果用了 `random()`，
**每个人跑出来的数字都不一样** —— 论文里的截图、答辩时的看板、自检的阈值全部对不上。
更糟的是：脚本跑完**不报错**，只是数据悄悄不对。

**方案**

**① 用确定性算法（取模）而不是 `random()`。**
报名生成按 `org_id = 1 + (g % 6)` 这类取模规则铺开，同一份脚本在任何机器上结果一致。
排序打破并列时用 **id** 而非中文名（中文串排序依赖 collation）。

**② 脚本末尾放 9 条 `RAISE EXCEPTION` 断言**，不满足就**整批回滚并报错**，
不留下「看起来跑成功了但数据是半成品」的库：

| 活动数 ≥ 386 | `sql/07_demo_scale.sql:836` |
| 学生数 ≥ 1000 | `:839` |
| 时长口径一致（`student_info` 合计 = `APPROVED` 明细合计） | `:851` |
| 学院不为空且学院合计 = 总时长 | `:860` |
| 公益等级恰好 6 档 | `:868` |
| 无活动超名额 | `:877` |
| 无孤儿时长 | `:886` |
| 演示账号时长非 0 | `:893` |
| 演示账号有标签 | `:898` |

全过时打印（`:901`）：

```text
[07 自检] 全部通过：学生 1500 人、活动 386 场、报名 10719 条、累计时长 19319.3 小时（演示账号 22.6 小时 / 标签 热心志愿者,长期坚持型,大型活动型）
```

**③ 整条重建链约 16 秒**，且顺序被明确固化 —— `04` 是 `07` 的硬前置、
`12` 必须放最后（否则 `07` 的名额回填会把 `12` 定的 20/35/18 改掉）。

**证据**

## 11. 20 项一致性自检脚本 —— 只读、可当场跑、结果确定

## 12. 前端工程硬约束 —— 三条踩过的坑被固化成规则
