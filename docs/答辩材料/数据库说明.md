### 三处答辩常被追问的设计点

**① 为什么 `attendance_record` 表里没有 `hours` 列？**
实得时长由「签退 − 签到」**实时算出**，避免与两个时间字段漂移。
出处：`docs/ER图.md:429`。

**② 为什么 `activity_signup.student_id` 指向 `student_info.id` 而不是 `sys_user.id`？**
后续所有报名、时长都挂在这份**档案**上而不是账号上 —— 账号可以换、档案不变。
出处：`docs/ER图.md:397`、`:561`。

**③ 为什么取消报名不改 `deleted`？**
`uk_activity_student(activity_id, student_id)` 是全量唯一约束，若取消时软删除、
重新报名时再插新行就会撞约束。所以拍板 **A7：取消 = 改 `status = 'CANCELED'`、复用同一行**。
出处：`docs/待办清单.md:220`（A7）、`docs/ER图.md:408`。

### 3.4 外键行为

- 全部外键都是**默认行为（`NO ACTION`）**，脚本里**没有任何 `ON DELETE CASCADE` / `ON UPDATE CASCADE`**。
- 删除一律走应用层的**逻辑删除**（`deleted = 1`），不靠数据库级联。
- ⚠️ 这曾经导致一个**缺陷 B31（删除用户不级联）**：`DELETE /api/v1/system/users/{id}` 只置
  `sys_user.deleted = 1`，该学生的 `student_info` / 报名 / 时长仍留在库里并**继续计入看板**。
  **该缺陷已于 2026-09-25 修复并实测闭环**，见下。

> ### ✅ B31 已修并实测闭环（2026-09-25）
>
> `DELETE /api/v1/system/users/{id}` 现在**同事务级联**软删 `student_info` / 报名 / 签到 /
> `service_duration`，并按 `sql/09` 第 ⑦ 项**同一谓词重算** `signed_count`
> （跨模块走「`vcp-system` 声明端口 + 上层实现」，照既有 `OrgLookupPort` 套路；
> 且是**必需注入**而非可缺省 —— 缺实现时安静跳过就是静默的半个级联）。
>
> **口径（别再改回去）**：报名走**逻辑删除 `deleted = 1`、保留原 `status`**，
> **不是**置 `CANCELED` —— 因为看板 `enrolled` 的口径是
> `COUNT(*) FROM activity_signup WHERE deleted = 0`，`CANCELED` 行仍会被数进去。
>
> **对照证据**：同一个 `verify.ps1`，修复前跑一轮就漂（报名 10,719→10,720、
> 时长 19,319.3→19,321.8、学生 1,503→1,504），修复后跑一轮**不漂**；
> `sql/09` 仍为「检查项总数 20，违规合计 0」。顺带修掉同族缺口
> `PortraitAggregateMapper.selectTagCounts` 缺 `si.deleted = 0`。
>
> **仍未做（如实记录）**：① `sql/09` **未加**「业务记录属于已逻辑删除的用户」这一项，
> 检查项数**仍是 20**；② 修复**不追溯**存量脏数据，靠重跑整链清（实测 **9.7 秒**）。
> **2026-09-26 补**：唯一一处已知存量实例（学生 96 的一笔被 e2e 误批的时长，连同其画像快照滞后）

> 累计时长回到 **19319.3**、标签分布回到 **1471 / 1380 / 392 / 286 / 231 / 222 / 200 / 165**。

| **CHECK 约束** | **0 个** | `Select-String -Path 'sql/*.sql' -Pattern '\bCHECK\s*\('` → **零命中** |
| **触发器 TRIGGER** | **0 个** | `-Pattern 'CREATE\s+(OR\s+REPLACE\s+)?TRIGGER'` → **零命中** |
| **视图 VIEW** | **0 个** | `-Pattern 'CREATE\s+(OR\s+REPLACE\s+)?VIEW'` → **零命中** |
| **乐观锁列** | **0 个**（无 `version` / `revision` 列，实体上无 `@Version`） | `-Pattern '\bversion\b|\brevision\b|@Version'` → **零命中** |

> 复现命令（只读，可在答辩现场跑）：
> ```powershell
> Select-String -Path 'sql/*.sql' -Pattern '\bCHECK\s*\(','CREATE\s+TRIGGER','CREATE\s+VIEW','\bversion\b'
> # 期望：四条 pattern 全部零命中
> ```

**为什么不做 —— 每一条都有明确理由，不是遗漏：**

1. **没有 CHECK**：状态字段的取值校验放在**应用层枚举**里（`vcp-common` 的 10 个状态枚举，
   码值与 `sql/03_init_data.sql` 的 `sys_dict` 种子**逐条核对过**）。
   好处是错误码可以带中文文案（如 `30006`「名额已满」），数据库 CHECK 做不到。
   出处：`docs/待办清单.md:297`（B1）、`vcp-common/.../ErrorCodeEnum.java`。
2. **没有触发器**：`update_time` 由 **MyBatis-Plus 字段自动填充**维护
   （PostgreSQL 没有 MySQL 的 `ON UPDATE CURRENT_TIMESTAMP`）。
   出处：`docs/ER图.md:173`、`docs/待办清单.md:299`（B2）。
3. **没有视图**：看板统计是**只读聚合 SQL**，写在 `vcp-analytics` 的
   `AnalyticsMapper.java` 里（用 `@Select` + `FILTER` + `generate_series`），
   不落成数据库视图 —— 视图会引入「改了视图要重建、版本管理麻烦」的额外负担。
4. **没有乐观锁列**：并发占名额改用**原子 UPDATE**（见下），
   `volunteer_activity` 没有 `version` 列，也不用行锁。
   出处：`docs/待办清单.md:205`（A3 原文：「也不用行锁（`volunteer_activity` 没有 `version` 列）」）。

**那并发是怎么保证的？** —— 靠**一条 SQL 的原子性**，不靠锁：

```sql
-- volunteer-cert-portrait-server/vcp-volunteer/.../mapper/VolunteerActivityMapper.java:35-36
UPDATE volunteer_activity SET signed_count = signed_count + 1, update_time = NOW()
 WHERE id = #{id} AND deleted = 0 AND (max_count <= 0 OR signed_count < max_count)
```

**影响行数为 0 即「已满」**（返回错误码 `30006`）。这一条同时解决了 TOCTOU
（先查再写的竞态窗口）与不限名额（`max_count <= 0`）两种情况。
出处：`docs/待办清单.md:203`（A3 决策原文）、`VolunteerActivityMapper.java:26`~`:36`。

## 六、一致性自检（可当场演示）

## 八、一句话速答（答辩现场备用）

| 可能的提问 | 一句话回答 |

| 几张表？ | 16 张，按 6 个业务域分组，`vcp-analytics` 无独立表。 |
