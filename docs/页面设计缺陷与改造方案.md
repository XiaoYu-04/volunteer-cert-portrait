## 零、开工前必读：三处「需求与原设计相冲突」的地方

这套 UI 是**从原型逐条移植**的「风格 12 · 新中式水墨风」（`docs/前端进展与待办.md:50-57`），
其中若干条被明确写成了**视觉约束**，而本次需求恰好要动它们。**动手前必须先跟用户确认**，
不要默默推翻——代码注释里满是「这是刻意选择，不要统一掉」这类警告。

### 冲突 1：「页面看去来过于锐利」 ⟷ 「零圆角是这套语言刻意定的骨架」

现状证据：

- `src/styles/tokens.css:24` —— `--r-sm:0; --r-md:0; --r-lg:0;`，**整个圆角刻度全为 0**。
- `src/styles/base.css:36-37` 注释原文：
  > 方角是这套水墨语言的骨架（`--r-*` 全 0），焦点环也必须是方的：
  > 原来的 `border-radius:3px` 会让按钮/输入框的焦点环变成圆角，和零圆角语言打架。
- `docs/前端进展与待办.md:57` 把它列为「视觉约束：**零圆角**、细墨线分隔而非卡片阴影、区块间距 88px……」

全仓库 `border-radius` 只有 4 处命中，其中非零的**只有 1 处**：
`ink.css:325` 的 `border-radius:50%`（单选框是圆的）。其余是 `ink.css:295` 的显式 `0`、
`options.js:90` 的图表 tooltip 显式 `0`、以及 `base.css:37` 注释里被删掉的历史值。

**换句话说：现在没有任何「圆角刻度」可用**——`--r-*` 三个令牌**定义了但全代码零引用**。
要做圆角必须同时（a）给刻度赋非零值、（b）改掉 `base.css:36-37` 的焦点环决定、（c）决定图表
`borderRadius:[6,6,0,0]` 是否跟着调。**这是设计语言层面的反转，需要用户明确点头。**

可选的软化路线（建议让用户选）：

| 方案 | 做法 | 代价 |
|---|---|---|
| A. 引入小圆角刻度 | `--r-sm:2px / --r-md:4px / --r-lg:6px`，只用在按钮/输入框/标签等**交互件**，面板与分隔线保持方角 | 改动集中在 `ink.css`，可控；但「水墨方角」辨识度下降 |
| B. 保持零圆角，改用别的维度去「锐利」 | 墨色从纯 `#1A1A1A` 略微提亮、细墨线降对比、加大留白与字距、给面板加极轻底色分层 | 不违背原语言；但「锐利」是主观感受，效果需实拍对比验证 |
| C. 全面圆角化 | 整站统一 6–8px | 与原型语言正面冲突，`base.css` 的整套论证要重写 |

### 冲突 2：「首页右边留白太多，插入雷锋图片」 ⟷ 「大量留白」是这套语言的基调

`tokens.css:4` 写明「**大量留白**、细墨线分隔、竖排装饰题字、印章式标签，区块间距 88px」，
`--sec-pad:88px`、`--wrap:1180px`。首页（`student-home`）正是一张很长的营销式落地页，
其 hero 区**右侧只有一竖排装饰字「志愿服务数据」，其余为空**——用户说的「留白太多」指的就是这类区域。

要放图就会正面撞上「大量留白」这条基调。**而且还有素材来源问题**（见冲突 3）。

### 冲突 3：图片素材从哪来 —— 仓库里几乎没有图，且**没有静态资源管线**

实测（已逐项核对）：

- **没有 `src/assets/` 这个目录**（`src/` 下只有 `api components composables directives layouts
  mock router stores styles utils views`）。
- 全仓库**唯一的源图片文件是 `public/favicon.ico`**。
- 全 `src/` 里 **0 处** `import ... from '*.png|jpg|svg'`、**0 处** `new URL(..., import.meta.url)`、
  **0 个内联 `<svg>` 元素**。唯一的 `new URL(` 在 `vite.config.js:1`（给 `@` 别名用的 `node:url`）。
- 唯一的 `background-image` 是 `ink.css:313` 的棋盘格，用 CSS `linear-gradient` 画的，不是文件。
- 图片一律是**运行时字符串 URL 直接绑到 `:src`**。最标准的范例是
  `components/biz/ActivityGridCard.vue:38-47`：

  ```html
  <img v-if="activity.cover" :src="activity.cover" :alt="`${activity.title}封面`" loading="lazy" />
  <div v-else class="ink-agc-fallback">…印章式占位…</div>
  ```

  路径来自接口 `cover` 字段（`ActivityPublishView.vue:120`：`coverImages.value[0]?.fileUrl || ''`），
  由后端 `/uploads/...` 提供（代理见 `vite.config.js:118-122`）。
  ⚠️ **mock 数据里活动根本没有 `cover` 字段** —— 所以 mock 模式下首页「本期志愿活动」
  显示的全是印章占位块。**配图不能指望从接口来。**

所以「插入雷锋图片」不是「找个 img 标签放上去」，而是要**先决定素材从哪来**：

| 方案 | 做法 | 说明 |
|---|---|---|
| 自绘水墨风 SVG 插画（**推荐**） | 内联 SVG 画水墨笔触的志愿者剪影/群像 | 无版权与肖像权风险，可随令牌改色，与「新中式水墨风」自洽。代价：仓库首次出现内联 SVG |
| 用户提供图片文件 | 放进 `public/`，按**唯一既有先例**（`index.html:5` 的 `<link rel="icon" href="/favicon.ico">`）以纯字符串 `"/leifeng.jpg"` 引用 | 零构建配置。不要新建 `src/assets/` —— 那会引入本项目**第一个** `import`/`new URL` 式资源引用，没有先例可抄 |
| 网上找雷锋照片 | 直接下载一张照片放进 `public/` | ⚠️ **不建议**：雷锋照片涉及肖像权/著作权归属，且与水墨风不搭；答辩场合公开使用风险更高 |

**若走位图方案，务必按既有图像处理惯例**：细墨线 `1px solid var(--c-line)` 描边 + **零圆角**，
配合固定 `aspect-ratio` 框 + `object-fit:cover`（先例：`.ink-agc-cover{aspect-ratio:16/9;overflow:hidden}`
at `ink.css:108-112`，以及 `ActivityDetailView.vue:255-263` 的 `.activity-cover img`）。
放进 `.hero-side` 的话，它会是**全产品第一个具象图像**，别让它显得像贴上去的。

## 二、MCP：Open Design 的连不上与修复

用户在需求里写了「调用 Open Design 完成设计」。**当前 MCP 连不上，原因是握手超时。**

### 现象与证据

`~/.claude.json` 里有 `open-design` 这个 MCP server：用 Electron 主程序以
`ELECTRON_RUN_AS_NODE=1` 当 node 跑 `daemon-cli.mjs mcp`，并连命名管道 sidecar。
配置本身是**对的**（`C:\Apps\Open Design\resources\app\prebundled\daemon\daemon-cli.mjs` 存在，
管道 `\\.\pipe\open-design-sidecar-218fafc6d33bc1981436ec172cc017bd` 也确实在）。

VSCode 扩展日志（`%APPDATA%\Code\logs\<时间戳>\window1\exthost\Anthropic.claude-code\Claude VSCode.log`）原文：

```
17:45:49  MCP server "open-design": Starting connection with timeout of 30000ms
17:46:19  MCP server "open-design": Connection timeout triggered after 30010ms (limit: 30000ms)
17:46:19  MCP server "open-design": Connection failed after 30011ms (CONNECT_TIMEOUT)
```

### 根因

首次 spawn 要冷启动一个 Electron 进程再引导 daemon，**握手超过 30 秒上限**被判失败；
而这个失败状态在**当前会话内被缓存**（`WaitForMcpServers` 显示 `failed=open-design` 而非 `pending`），
所以**会话内重试永远不会成功**。

反证：同机器上 `claude mcp list` 显示 `open-design: … √ Connected` —— 它是一次独立健康检查、
且此刻进程已热，说明**配置与服务都没坏，纯粹是冷启动超时**。

### 修法（按代价从低到高，**先试第 1 步**）

> ⚠️ **更正**：本文件初稿写过「必须重启会话才能重连」，**那是错的**。
> 已核对官方文档：失败后界面会提示 `MCP server "open-design" disconnected · open /mcp to reconnect`，
> **`/mcp` 对话框里可以直接重连**，不必重启会话。

**第 1 步（零代价，先试这个）**：在 Claude Code 的聊天面板里输入 **`/mcp`**，
在弹出的对话框里重连 `open-design`。文档原文（`code.claude.com/docs/en/mcp`）：

> Reconnect: on a `cached` server, Claude Code connects it now rather than on its first tool call and keeps
> the entry. On a connected or failed server, Claude Code **reconnects it and also discards the entry**.

文档**没有**说失败状态会被会话级记忆（唯一的会话级缓存是远端 HTTP/SSE server 的工具列表发现缓存，
默认关闭），所以 `/mcp` 重连这条路是通的。

**第 2 步（第 1 步仍超时才做）**：把启动超时从默认 30 秒调大。
在 `~/.claude/settings.json` 的 `env` 块里加：

```json
{ "env": { "MCP_TIMEOUT": "120000" } }
```

核实过的细节（由子代理对照官方文档 + 解出扩展内 `claude.exe` 的取值逻辑确认）：

- 变量名 **`MCP_TIMEOUT`**，单位**毫秒**，**默认 30000**（文档未写默认值，该值从二进制里解出：
  `MCP_TIMEOUT` 未设或 ≤0 时回落到 30000；上限 2147483647）。它正是日志里
  `Starting connection with timeout of ${MCP_TIMEOUT}ms` 的那个数。
- 放**用户级** `~/.claude/settings.json`（不是 `~/.claude.json`）。官方 VS Code 文档明确
  「settings.json 在扩展与 CLI 之间共享」，且扩展自己的 `claudeCode.environmentVariables`
  的说明也写着「Prefer setting environment variables in Claude's settings.json」。
- 优先级：**settings.json 的 `env` 覆盖 shell 环境变量**。对 VS Code 扩展尤其应该用 `env` 块——
  从图形界面启动的 VS Code 可能根本没继承 shell 环境。
- 改完 `env` 后**必须新开会话**才生效（已经 spawn 过的 server 不会重新 spawn）；
  验证方法是日志里出现 `Starting connection with timeout of 120000ms`。
- ⚠️ **不要把 `timeout` 加到 `.mcp.json` / `~/.claude.json` 的 server 条目上** ——
  那个字段管的是**工具执行**超时，**不是启动握手**，解决不了本条问题（已核对二进制：启动路径读的是
  `MCP_TIMEOUT`，per-server `timeout` 只在工具超时的取值路径里被读）。
- 若调到 120 秒后**仍在限额处精确超时**，那就是真的冷启动慢，属服务端问题
  （正解是让该 MCP server 立刻应答 `initialize`、把 Electron sidecar 推迟到首次工具调用再加载），
  继续加大超时只是拖延。

**重新连上后**，确认 `open-design` 的工具已挂到工具列表上，再开工。

### 1. 登录页现状（诉求 1）—— 机械成因已定位

**布局：整屏 50/50 两栏网格**（`ink.css:555`）：

```css
.auth{min-height:100vh; display:grid; grid-template-columns:1fr 1fr}
```

**「黑区留白太多」的直接机械原因**是 `ink.css:556-559` 的 `justify-content:space-between`：
`.auth-aside` 是 `flex-direction:column` + `space-between`，而它**恰好只有三个子元素**，
于是三块内容被强行顶到**最上 / 最中 / 最下**，中间全是空的：

```css
.auth-aside{background:var(--c-ink); color:rgba(255,255,255,.78);
            padding:64px 56px; display:flex; flex-direction:column;
            justify-content:space-between}
```

`--c-ink: #1A1A1A`（`tokens.css:13`）就是所谓「黑色区域」。

### 2. 首页现状（诉求 2）—— 右边空白的两个成因，已定位到像素

先确定「首页」指哪个：**是学生端 `src/views/student/HomeView.vue`**（`routes/student.js:9`，
`meta.title` 就叫「首页」）。两个控制台角色的落地页（`org/OrgDashboardView.vue`、
`admin/DashboardView.vue`）是 `.panel` 纵向堆叠、每块都占满宽度，**没有专属的空右列**，
所以诉求 2 说的不是它们。

截图：`docs/screenshots/student/student-home-1440.png`（真后端口径，2026-09-26 09:04）。
区块顺序：hero → 6 格指标 → 全年趋势（折线 + 饼）→ 本期活动（6 卡）→ 学生公益画像（8 标签）→
志愿服务流程（4 步）→ 学院排行 + 组织活跃度 → 时长审核与签到 → 页脚。

**成因 1：居中容器在视口两侧留出装订线。** `base.css:75-80` 的 `.wrap` 是
`max-width:var(--wrap)` = **1180px**（`tokens.css:23`），减掉 `--pad:28px` 两侧内边距 →
可用内容宽 **1124px**。在 1440px 视口下，**每侧各空 130px**。`HomeView.vue:79` 用
`<div class="wrap">` 包住整页，所以**每个区块都继承这个留白**。

**成因 2（主因）：hero 的右 3 栏结构上几乎是空的。**
`HomeView.vue:62-77` 的 hero 是 12 栏网格，`ink.css:31-35`：

```css
.hero-in{display:grid; grid-template-columns:repeat(12,minmax(0,1fr)); gap:36px}
.hero-main{grid-column:1 / span 9}
.hero-side{grid-column:10 / span 3; display:flex; justify-content:flex-end}
```

第 10–12 栏 = **1124px 的 25%，约 281px 宽**，而这一整栏里**只有一个 22px 的竖排字符串**
`.vtitle`（`ink.css:35-39`，`writing-mode:vertical-rl`，右对齐，带一条细墨线 `border-right`）。
行高由 `hero-main` 决定：h1 是 `clamp(32px,4.6vw,58px)` × `line-height:1.3` × 两行 ≈ 150px，
加上 kicker/sub/按钮，整行约 **400–420px 高**。

→ 净结果：**首页右上角一块约 281×400px 的纯空白矩形**，只有一根细墨线穿过。
这就是用户说的「右边留白太多」。

**加剧因素**：本该填满 9 栏的左侧文字**自己也提前截断** ——
`.hero h1{max-width:16em}`（`ink.css:44`）、`.hero-sub{max-width:34em}`（`ink.css:47`），
所以左栏也没填到第 9 栏。

### 4. 设计系统的「死令牌」（改造时可安全清理）

实测**定义了但全代码零引用**：`--r-sm` / `--r-md` / `--r-lg`、`--shadow-1`、`--c-press`、`--sp-10`。
另外**没有字号令牌**——`--fs-*`/`--lh-*`/`--fw-*` 都不存在，`ink.css` 里字号是逐条硬编码的
（13px×18 处、14px×17 处、12px×16 处……），层级靠字号+颜色+字距而非字重。

`--shadow-1` 零引用意味着**全站静态元素没有任何阴影**，层次完全由三种粗细的墨线承担：
`1px solid --c-ink`（结构性：表格顶线、指标块顶线）/ `--c-line`（容器：面板、输入框）/
`--c-line-2`（面板内行分隔）。唯一的阴影是 `--shadow-pop`，只用在 `.ink-toast`（`ink.css:417`）
与图表 tooltip。

## 五、缺陷清单（逐条带 `file:line`，按严重度排序）

> 来源：4 个侦察子代理分工核查（设计底座 / 登录页+首页 / 两端角色 / 缺陷全扫）。
> 全部为**读代码 + 读像素**得到，**尚未动手修**。凡标注「估算」的项需要实机测量确认。

### 🔴 高危 1 —— 表格文字被挤到逐字换行（对应诉求「字体溢出」+「页面排版」）

**机械原因**：`.ink-table` **没有 `table-layout`**（`ink.css:243`），
所以 15 个页面 `columns` 数组里写的 `width:'110px'` **全是建议值、不是约束**。
而 `.col-num` 是 `white-space:nowrap`（`ink.css:259`，等宽数字列不换行）→ 它**占满自己要的宽度**，
亏空就全被**能逐字断行的中文列**吸收，中文列的 min-content 可以塌到**一个字宽**。

而 `ink.css:250-253` 的 `td` **既无 `overflow:hidden`、也无 `text-overflow:ellipsis`、也无 `word-break`**，
所以被挤的单元格是**换行**而不是截断 —— 于是出现「陈思／远」这种词组被劈开的样子。

**观测证据**（`.tmp-shots/out/1440-admin-users.png`）：**每一个姓名都断成两行** ——
`陈思/远`、`赵慧/敏`、`林诗/涵`、`王泽/宇`、`刘静/怡`、`张文/轩`、`李佳/琪`、`黄天/佑`、`周若/曦`。
姓名列声明 100px（`admin/UserManageView.vue:64`），实际塌到约 **60px**。
`1440-admin-durations.png` 里 `机械工程学/院`、`社区老年人智能手机课/堂` 同样被劈开，
而固定宽的时长/日期列却留着大片余裕。

**已确认现存**：`git diff 4bb57af..HEAD -- src/views/` **没有**任何 `width:'<n>px'` 变更。
同类页面：`admin/DurationAuditView.vue:48-58`、`org/AttendanceView.vue:29-39`、
`org/DurationSubmitView.vue:34-54`、`admin/LogView.vue:30-38`、`admin/PortraitView.vue:58-68`。

### 🔴 高危 2 —— 操作列比它要装的按钮还窄

`.col-actions{white-space:nowrap}`（`ink.css:260-261`）+ `.btn-sm`（`ink.css:237`）下，
2 字按钮 = 56px、4 字按钮 = 82px。实测三处**内容宽度超出声明宽度**：

| `student/MySignupsView.vue:72` | `220px` | 签到+签退+查看活动+取消报名 = **306px（超 86px）**（`:222-261`） |
| `admin/UserManageView.vue:70` | `250px` | 编辑+重置密码+停用/启用+删除 = **280px（超 30px）**（`:355-362`） |
| `org/ActivityManageView.vue:51` | `230px` | 发布/结束+取消+报名审核 = 最多 **250px（超 20px）**（`:175-188`） |

因为 `table-layout:auto`，这些列会**自己长大并从可换行的中文列偷宽度**——这正是高危 1 的燃料。

### 🔴 高危 3 —— 图片没有兜底，且演示包里一张图都没有（对应诉求「图片没有」）

**(a) 全项目没有一个 `<img>` 有 `@error` 处理**（`grep -rn "@error\|onerror\|naturalWidth" src/` → **0 命中**）。
全部 `<img>` 只有 5 个，其中 `components/biz/ActivityGridCard.vue:39-47` 的问题最典型：

```html
<img v-if="activity.cover" :src="activity.cover" :alt="`${activity.title}封面`" loading="lazy" />
<div v-else class="ink-agc-fallback">…印章式占位…</div>
```

占位块做得很好（`ink.css:118-127`），但它挂在 **`v-else`** 上 ——
**一旦 `cover` 是个非空但 404 的 URL，显示的是浏览器的碎图标，而不是这个占位块。**
另外 4 处（`org/ActivityManageView.vue:148`、`student/ActivityDetailView.vue:122` 与 `:210`、
`common/InkImageUploader.vue:96`）同样没有兜底。

**(b) 演示配置下整站不渲染任何照片。** `.env.production` 设 `VITE_USE_MOCK=true`（答辩用的独立演示配置），

- `InkImageUploader.vue:19-20` `canAdd = !mockMode && …` → 组织端也没法自己加图。

**(d) 空态没有插画**：`common/InkEmpty.vue:11-16` 只渲染一个 44px 的「空」字 + 文字
（`ink.css:354-360`）。品牌标识也全是 CSS 盒子 + 文字（`.seal` at `ink.css:16-21`），**没有图标系统**。
