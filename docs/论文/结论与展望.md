### 1.2 主要成果与技术要点

**（1）A1 与 A2 是两条互补约束，而非一条规则的两种说法。** 签到签退窗口（开始前 30 分钟开放
签到、结束后 30 分钟内必须签退，未签退记 `ABSENT`）管"**能不能**签到"；"1.5 倍预计时长封顶"
管"**最多能记多少**时长"。窗口允许的最大跨度为 `预计时长 + 1 小时`，换算成倍数即 `1 + 1/预计时长`：

| 活动预计时长 | 窗口允许的最大倍数 | 哪条约束更紧 |
|---|---|---|
| 0.5 小时 | 3.0 倍 | **1.5 倍封顶更紧**（窗口允许 1.5 小时，封顶只给 0.75 小时） |
| 1 小时 | 2.0 倍 | **1.5 倍封顶更紧** |
| 2 小时 | 1.5 倍 | 两者相等 |
| 4 小时 | 1.25 倍 | 窗口更紧（封顶不生效） |

即**预计时长小于 2 小时时，正是 1.5 倍封顶挡住了"短活动靠窗口刷时长"**；预计时长 ≥ 2 小时时
窗口才是更紧的约束（`docs/论文/03-详细设计.md:732-750`）。

**（2）名额并发控制把判断条件下推到 SQL。** 实现为
`UPDATE volunteer_activity SET signed_count = signed_count + 1 WHERE id = ? AND signed_count < max_count`，
**影响行数为 0 即判"已满"**（返回 `30006`）。这一条同时解决原子性与超卖：既无"先查再写"的
TOCTOU 窗口，也**不必加 `version` 列**（该表本来就没有），比 `SELECT ... FOR UPDATE` 还避免了
长事务持锁（`docs/待办清单.md:202-205`）。

**（3）用"权威值 + 快照"消解字段含义重复，并把冗余的代价显式量化。**
`student_info.total_duration` 与 `student_profile.total_duration` 含义重复，A5 拍板**前者为权威值、
后者仅作画像快照**（`docs/待办清单.md:211-213`）。更进一步，本文把所有**刻意的冗余与派生**
（`signed_count`、两个 `total_duration`、`total_activities` 等）逐条列出并各配一项检查，
固化成 **20 项只读、可重复执行的一致性自检**（分 6 组：外键悬空、汇总与明细不符、状态与审核字段
矛盾、学院专业错配、时间异常、演示数据完整性），"违规合计 0"因此成为数据层验收标准，
也是答辩时可当场演示的证据（`sql/09_consistency_check.sql:385-389`）。

**（4）一处设计决策的连锁反应，以及由此暴露的最有价值的一个缺陷。** A7 决定
"取消报名 = 改 `status = 'CANCELED'`、复用同一行、`deleted` 保持 0"（`docs/待办清单.md:220-223`）。
决策本身是对的，但它把"**报名是否有效**"的判定从 `deleted` **转移到了 `status`**，而
`DurationRefMapper.selectSignupId` 仍只检查 `deleted = 0`，于是"待审核 / 已驳回 / 已取消"的报名
**也能开出时长**，且当时**没有撤销接口**。该 P0 缺陷由端到端流程测试打出，修复为反查 SQL 增加
`AND status IN ('APPROVED','COMPLETED')`，并**纠正了该处 javadoc 里与实现相反的前提**
（`docs/测试报告.md:179-188`）。与之配对的 A4 规定"驳回后可重新提交、审核历史只追加不覆盖" ——
**A4 与 A7 的共同取向是"保留历史、不改写过去"**。

**（5）公益画像：6 档等级 + 8 类标签，且规则与演示数据必须一起设计。** 等级按累计有效时长分为
普通 / 一星 / 二星 / 三星 / 四星 / 五星（阈值 3 / 6 / 10 / 20 / 40 小时）；标签分通用两类与类型
六类（校园服务 / 社区服务 / 环保公益 / 大型赛事 / 助老服务 / 文化传播），**类型标签互斥、最多一个**
（`docs/公益等级与标签规则方案.md:47-56`、`:83-95`）。三处细节保证可复现与可演进：**并列按分类 id
升序打破**（不用中文名 —— 中文串排序依赖数据库 collation）、**分类到标签按 `code` 映射而非中文名**
（改名不会静默错位）、**重算只写真正变化的行**（否则 1500 人规模下产生大量无意义写入并破坏幂等）。
规则取舍还与数据构造**同时**做出：类型标签不设"同分类 ≥ 2 次"下限的代价是"基于单次活动贴标签"，
因此同步给每个学生预设 1~2 个偏好分类（`docs/公益等级与标签规则方案.md:128-135`）。

**（6）跨模块协作走依赖倒置端口，而不是反向依赖。** 本项目统一用**调用方模块声明端口、
被调用方提供实现**解决"回读"造成的反向依赖：`OrgLookupPort` / `OrgCollegeCountPort` 由 `vcp-org`
实现；修 B31 时沿用同一套路，`StudentSignupPurgePort` / `StudentDurationPurgePort` 分别由
`vcp-volunteer` / `vcp-certification` 实现，编排在 `StudentArchivePurger.purgeByUserId`，由
`UserServiceImpl.deleteUser` 在**同一个 `@Transactional`** 里调用（`docs/后端进展与待办.md:209-210`、
`docs/下一步待办.md:553-558`）。端口是**必需注入而非可缺省**（缺实现时安静跳过就是"静默的半个
级联"，正是 B31 的缺陷形态）；`signed_count` 用一条 UPDATE **按 `sql/09` 第 ⑦ 项同一谓词重算**
而非逐行 −1。

### 1.4 工程与管理层面的收获

1. **模块边界是三人并行的前提。** 依赖规则让三条开发线各自动各自的模块，集成时发现的 4 个问题
   也都能定位到明确的归属方（`CLAUDE.md:87-89`、`docs/后端进展与待办.md:284-307`）。
2. **脚本必须确定性，口径一致性要靠机制而不是靠记性。** 演示数据一律用**取模**而非 `random()`、
   排序打破并列用 **id** 而非中文名，`sql/07` 重跑第二遍输出与第一遍**逐字相同**；而三条脚本
   顺序约束（`04` 是 `07` 的硬前置、学院字典只在 `10`、`12` 必须放最后）违反任何一条都**不报错**，
   只会让数据悄悄错位（`docs/测试报告.md:305`、`CLAUDE.md` 踩坑第 20 条）。
3. **"验证后发现不用改"同样是有效产出。** A9（`sys_user.status` 类型）原以为三层不一致，只读审计
   后发现 DB 存 `SMALLINT` 1/0、服务层枚举双向翻译、API 返回 `ACTIVE`/`DISABLED`、前端字典用
   英文码 —— **本来就对齐，明确"无需改动"**（`docs/待办清单.md:234-240`）。
4. **32 条踩坑的共同特征是"不报错但结果是错的"**，这决定了验证必须分层（`CLAUDE.md` 踩坑清单）。

## 二、展望

以下 9 项均为**真实存在**的未做项或已知限制，每条按「现状 / 为什么没做 / 打算怎么做」写。

**2.1 开启 Flyway 数据库迁移。** **现状**：`spring.flyway.enabled: false`，建库仍靠 12 个手工脚本。
**为什么没做**：表结构在开发期频繁变动，而**已执行脚本受 checksum 保护、不可再改**。**打算怎么做**：
答辩后冻结结构，先做 `V1__baseline.sql` 基线，再把 `05`/`06`/`07`/`11` 的补列重放为增量脚本，
在**空库**上验收"迁移链一次跑通、`sql/09` 仍为 0"。

**2.2 补自动化测试。** **现状**：后端 9 个模块的 `src/test` **全空、零单元测试**；前端**无组件测试**。
**为什么没做**：已拍板（C7）用"用例表 + 测试报告 + `sql/09`"替代单测，把时间优先投给闭环验证
（`docs/测试报告.md:214`）。**打算怎么做**：对 A1 时长计算、A3 占名额、A5 权威值累加、画像判定
四处**纯逻辑**补 JUnit，再把端到端断言改为可入库的集成测试（见 2.10）。

**2.3 补齐 `operation_log.target` 的写入侧。** **现状**：操作日志「操作对象」列**恒空** ——
`@OperationLog` 缺 `target` 属性。**为什么没做**：需各业务方法显式传对象 id，属**跨全部 Controller
的批量改动**，收尾阶段优先级低于闭环正确性（`docs/测试报告.md:212`）。**打算怎么做**：注解增加
`target` 并支持 SpEL，先补用户增删改与三类审核接口。

**2.4 把 6 档等级阈值收敛为配置表。** **现状**：阈值**硬编码在 3 处** —— `sql/04_demo_data.sql`、
`sql/07_demo_scale.sql`、`PublicWelfareLevelEnum.java`。**为什么没做**：规则方案建议"做成可配置
常量、不要散落在 SQL 与 Java 两处"，但演示数据脚本先于配置化落地，**这一条没有完全落地**
（`docs/公益等级与标签规则方案.md:172-173`）。**打算怎么做**：新增阈值配置，Java 侧枚举读配置、
SQL 侧调用同一份，并同步改 `sql/09` 第 19 项判据。

**2.5 接入组织资质材料与用户头像上传。** **现状**：活动图片上传已完成，而 `attachment.biz_type`
的 `ORG`（组织资质）与 `AVATAR`（用户头像）**已定义但未接入**。**为什么没做**：属计划书 P2 可选
功能，且资质材料的可见性口径当时未定（`docs/答辩前待办.md:107`）。**打算怎么做**：复用现有图片
上传的校验链（仅 JPG/PNG、≤ 5MB、`ImageIO` 识别真实格式），补按 `biz_type` 区分的可见性规则。

**2.6 实现志愿证书生成与活动收藏。** **现状**：两项均为计划书 P2 项，**未实现**。**为什么没做**：
与"时长认证闭环是否可信"这一核心目标无关；证书还涉及模板、编号、防伪与撤销等一整套口径
（`docs/答辩前待办.md:108`）。**打算怎么做**：证书以 `service_duration` 中 `APPROVED` 的行为唯一
来源、按"年份 + 学生 id + 序号"确定性编号；收藏用 `activity_favorite` 关联表加唯一约束实现。

**2.7 真机部署与 `nginx -t` 实测。** **现状**：部署文档与 `deploy/` 三件配置均已就绪，本机用
**按 `nginx.conf` 语义实现的 Node 替身**验了静态托管、history 回退、`/api` 反代与 `/uploads` 取图
（PASS 9 / FAIL 0）；但 **`nginx -t`、真 nginx 运行时行为、systemd 单元行为、公网 8080、HTTPS 与
"干净机器照文档走一遍"全部未实测**。**为什么没做**：本机（Windows）无 nginx 也无 Linux 环境。
**打算怎么做**：在干净 Linux 机器上照部署文档执行，先 `nginx -t` 再起服务，并验证 `vcp.service`
的 `$JAVA_OPTS` 展开 —— 该处曾发现 `ExecStart` 未引用 `$JAVA_OPTS` 的死配置，而本项目时间字段是
**无时区** `TIMESTAMP`，时区错了会影响签到窗口。

**2.8 对齐演示数据与运行期算法口径（画像标签漂 6 个 −1）。** **现状**：`verify.ps1` 第 5 步调
`POST /api/v1/portraits/recompute` 重写了 4 份画像的 `tags`，于是 `/portraits/distribution` 有
**6 个标签各 −1**（社区服务型 393→392、环保行动型 287→286、大型活动型 232→231、校园服务型
223→222、文化传播型 201→200、助老服务型 166→165）—— **既有的脚本与运行期算法口径差异，
不是 B31 的漂移**。**为什么没做**：根治要改脚本的标签生成并与 `PortraitTagEnum` 逐条对齐，
而它只影响"跑过 e2e 之后的库"，重跑整链（约 10 秒）即可恢复。**打算怎么做**：把脚本按中文分类名
判标签的写法改为按 `code` 映射、并列按分类 id 升序，并加一条"标签分布与运行期重算一致"的断言。

**2.9 收尾"删除用户级联"（自检项与存量数据）。** **现状**：B31 已落地并实测闭环（同事务级联软删
`student_info`、逻辑删除其报名且**保留原 `status`**、按 `sql/09` 第 ⑦ 项同一谓词**重算**
`signed_count`、作废签到、软删时长；修复前跑一轮即漂 10719→10720、19319.3→19321.8、1503→1504，
修复后不漂），但 `sql/09` **未新增**对应检查项（总数仍是 20）、修复**不追溯**存量脏数据。
**为什么没做**："20 项"被大量文档引用，改项数需统一评估；存量脏数据靠重跑整链清理。
