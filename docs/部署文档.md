## 一、目标架构

```
浏览器
  │
  ▼
Nginx（80/443）── 静态文件 /var/www/vcp（前端 dist/）
  │                 └─ /api/ 反代 → http://127.0.0.1:8080
  ▼
Spring Boot jar（JDK 21，端口 8080，无 context-path）
  │
  ▼
PostgreSQL 18（volunteer_cert_portrait 库，16 张表）
```

三个要点决定了下面所有配置：

1. **后端没有配 `context-path`**，接口前缀就是 `/api/v1/...`，所以 Nginx 的 `/api/` 反代要**原样透传路径**。
2. **前端是 SPA，用 history 路由**（`/student/profile` 这种路径磁盘上不存在），Nginx 必须做 `index.html` 回退。
3. **前后端同源**（都从 Nginx 出），所以浏览器不发跨域请求，CORS 在部署形态下实际不会命中。

## 二、前置条件

| 组件 | 版本 | 说明 |
|---|---|---|
| JDK | **21** | `pom.xml` 的 `<java.version>21</java.version>`。Boot 4 要求 21，**17 不行** |
| Nginx | 任意较新版本 | 只做静态托管与反代 |
| PostgreSQL | 18 | 复用现有云库，或自建 |
| Node.js | 24（`^22.18.0 \|\| >=24.12.0`） | **只在构建机需要**，服务器上不需要 |

### ⚠️ 坑 1：机器上有多个 JDK 时，`JAVA_HOME` 和 `java` 未必指向 21

实测（2026-09-24，开发机）：`JAVA_HOME` = `C:\Apps\java\jdk-17.0.17`，`mvn -version` 报的也是 17，
而机器上其实另装了一份 JDK 21 —— 只是没被用。部署机上同理：**装完 21 一定要确认**

```bash
java -version        # 必须是 21.x
echo $JAVA_HOME
```

`deploy/vcp.service` 里 `ExecStart` 写的是绝对路径 `/usr/bin/java`，就是为了不吃 PATH 的亏；
若机器上路径不同，改成实际的绝对路径。

## 四、后端

### 4.1 打包（在构建机上）

```bash
cd volunteer-cert-portrait-server
mvn -B package -DskipTests
# 产物：vcp-boot/target/vcp-boot-1.0.0.jar（fat jar；2026-09-24 实测 40.8 MB）
```

> **Windows 上打包前先停掉正在运行的实例** —— 运行中的 jar 会锁住文件，repackage 会报
> `Unable to rename 'vcp-boot-1.0.0.jar' to '...jar.original'`。

### 4.2 上传

```bash
sudo useradd -r -s /usr/sbin/nologin vcp
sudo mkdir -p /opt/vcp/config /opt/vcp/uploads
sudo cp vcp-boot-1.0.0.jar /opt/vcp/
sudo cp -r volunteer-cert-portrait-server/uploads/demo /opt/vcp/uploads/
sudo mkdir -p /opt/vcp/docs && sudo cp -r docs/* /opt/vcp/docs/   # 可选：vcp.service 的 Documentation= 指向这里
sudo chown -R vcp:vcp /opt/vcp
```

`/opt/vcp/uploads/` 保存用户上传和演示图片；`application.yml` 的
`vcp.upload.dir=./uploads`（`application.yml:128`）与 systemd 的 `WorkingDirectory=/opt/vcp`
共同决定该路径 —— **这两处必须同时对**，否则 Nginx 的 `alias /opt/vcp/uploads/` 会指向空目录。
仓库里 `volunteer-cert-portrait-server/uploads/demo/activities/` 现有 3 张演示图
（`children-reading.png` / `community-elder-care.png` / `river-cleanup.png`，各约 2~2.9 MB），
`11`/`12` 号 SQL 的图片记录指的就是它们。
Nginx 配置已经把 `/uploads/` alias 到该目录，并把 `client_max_body_size` 调到 6MB
（对应 `application.yml:13-14` 的 `max-file-size: 5MB` / `max-request-size: 6MB`）。

### 4.3 配置凭证（**prod 必须外置覆盖演示默认值**）

> ⚠️ **2026-09-26 起的前提变了**：`application.yml` 里现在带着一个**明文演示默认口令 `123456`**
> （共享演示库的刻意取舍，见根 `README.md` 与 `docs/待办清单.md` 的「明文凭证」一节）。
> **部署到真实环境时必须覆盖它** —— 用下面的 `vcp.env` 或 `config/application-local.yml`；
> 不覆盖就等于生产在用一个公开口令。

`application.yml` 的 `spring.config.import` 已按序尝试四个位置，部署场景用**最后一条**：

```
optional:file:./config/application-local.yml
```

配合 `vcp.service` 的 `WorkingDirectory=/opt/vcp`，即读 `/opt/vcp/config/application-local.yml`。
内容照 `vcp-boot/src/main/resources/application-local.yml.example`：

```yaml
vcp:
  db:
    username: postgres
    password: "在这里填口令"    # ⚠️ 必须加引号
```

或者用环境变量（**优先级更高**，也是 `vcp.service` 里采用的方式）：

```bash
# /opt/vcp/vcp.env，权限 600、属主 vcp
VCP_DB_USERNAME=postgres
VCP_DB_PASSWORD=这里填口令
```

> ⚠️ **坑 2：口令必须加引号。** YAML 会把以 0 开头的数字串当**八进制整数**解析
> （实测 `012345` → `5349`），口令就错了。
>
> ⚠️ **坑 3：缺凭证不会启动失败。** 实测确认：`@ConfigurationProperties` 绑定对解析不了的占位符
> **不报错**，会把它当普通字符串用，应用照常启动 —— 要到**第一次访问数据库**才以认证失败暴露。
> 所以「服务起来了但一登录就报错」时，第一件事是检查凭证文件在不在、口令对不对。
>
> ⚠️ **坑 4：真实凭证不得写回被跟踪的文件。** 仓库是**公开仓库**，明文口令进过 git 历史
> （删文件删不掉历史，只有轮换口令才能让旧口令失效 —— 2026-09-23 已轮换过一次）。
> `application-local.yml` 与 `vcp.env` 都必须 gitignore。
> **唯一例外是上面那个演示默认值 `123456`**：它是 2026-09-26 为了让任何人 clone 后零配置
> 连演示库而**刻意**公开的，只允许用于演示库；真实环境一律按本条处理。

### 4.4 限制后端只监听本机（**已默认做在 `vcp.service` 里**）

`application.yml` **没有配 `server.address`**（只有 `server.port: 8080`，`application.yml:1-2`），
裸起 jar 时后端监听 `0.0.0.0:8080` —— 也就是 **8080 直接暴露在网上**，别人可以绕过 Nginx 直接打后端。

**`deploy/vcp.service` 的 `ExecStart` 已经带上 `--server.address=127.0.0.1`（做法①）**，
所以用 systemd 起就是收口状态，不需要额外操作。想改的话二选一：

```bash
# 做法①（推荐，vcp.service 已采用）：写进启动参数
java -jar vcp-boot-1.0.0.jar --server.address=127.0.0.1
#   也可以写进 /opt/vcp/config/application-local.yml：
#     server:
#       address: 127.0.0.1

# 做法②：用防火墙/云安全组挡掉 8080 的外部访问
```

> ⚠️ 想让**别的机器直连 8080**（例如临时用开发口径看 `/doc.html`），
> 要把 `vcp.service` 里那一段删掉或改成 `0.0.0.0` —— 否则只有服务器本机能连。
> 改完 `sudo systemctl daemon-reload && sudo systemctl restart vcp`。

### 4.5 起服务

```bash
sudo cp deploy/vcp.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now vcp
sudo systemctl status vcp
sudo journalctl -u vcp -f
```

> ⚠️ **坑 8（2026-09-25 修正）：`Environment=` 不会自动进 `ExecStart`。**
> 单元文件里的 `Environment="JAVA_OPTS=-Xms256m -Xmx512m -Duser.timezone=Asia/Shanghai"`
> 只有在 `ExecStart` **显式引用 `$JAVA_OPTS`** 时才生效；原先没引用，导致**堆上限与时区都没生效**
> （JVM 用默认堆；时区错了会直接影响看板趋势图与签到窗口 —— 本项目时间字段是
> `TIMESTAMP`（无时区）+ `LocalDateTime`，见 `CLAUDE.md` 踩坑第 10 条）。已修正为
> `ExecStart=/usr/bin/java $JAVA_OPTS -jar ...`。依据：systemd.service(5) 写明
> 「`$FOO` 独立成词时按空白拆成 **0 个或多个**参数」，所以 `JAVA_OPTS` 为空也不会留下空参数。
> 首次部署后核对一次：`systemctl show vcp -p ExecStart`、`ps -ef | grep vcp-boot`。
> （另一条 `Environment="JAVA_TOOL_OPTIONS="` 是 **JVM 自己认**的变量，置空是为了挡住外部继承，与
> `JAVA_OPTS` 不是一回事，别删。）

`vcp.service` 里设了 `SPRING_PROFILES_ACTIVE=prod`，对应 `application-prod.yml` 的三处上线收口：

| 收口项 | 效果 |
|---|---|
| `vcp.cors.allowed-origin-patterns` | 由 `*` 收紧为白名单（同源反代下不会命中） |
| `knife4j.enable=false` | 文档页 `/doc.html` 与 `/v3/api-docs` **不再免登录** |
| `logging.level.com.vcp` | 由 `debug` 调回 `info`，不再全量打印 SQL |

> ⚠️ **坑 5：不激活 prod，这三项一律不生效。** 开发/演示行为与改动前逐项一致 ——
> 也就是说，忘了加 `SPRING_PROFILES_ACTIVE=prod` 的话，接口文档会对着公网免登录敞开。
>
> ⚠️ **坑 6：`application-prod.yml` 的 `allowed-origin-patterns` 是占位值**
> （`https://vcp.example.edu.cn`），**部署前必改成实际域名**。同源反代下这一项其实不会命中，
> 但留着占位值不体面，且将来若改成前后端分域部署就会真的用上。

## 五、前端

### 5.1 ⚠️ 坑 7：构建前必须把 `VITE_USE_MOCK` 改成 `false`

**这是整个部署流程最容易犯的错**，因为**它不报错**：`VITE_USE_MOCK=true` 的产物页面能正常打开、
有数据、有图表，看起来一切正常 —— 只是**根本不请求后端**，数字是 mock 的
（12,480 报名 / 86,420 小时），与真库（10,719 / 19,319.3）不是同一套。演示时和论文里的数字对不上。

**推荐做法：不动入库的 `.env.production`，用 `.env.production.local` 覆盖**（`*.local` 已被
`.gitignore` 覆盖、不入库）。`vite build` 的加载优先级是 `.env.production.local` > `.env.production`，
所以这样既能出真后端口径的包，又不会把「纯前端独立演示」那份配置改掉：

```bash
cd volunteer-cert-portrait-web
# 1) 建临时覆盖文件（构建完就删）
printf 'VITE_API_BASE_URL=/api\nVITE_USE_MOCK=false\n' > .env.production.local
# 2) 构建
npm ci
npm run build          # 产物在 dist/
# 3) 校验（见下）
# 4) 删掉覆盖文件，恢复「不改入库文件」的状态
rm .env.production.local
```

> 也可以直接改 `.env.production` 里的那一行 —— 效果一样，但**它是要入库的文件**，
> 改完记得改回去，否则会把「纯前端独立演示」的默认口径弄丢（答辩兜底要用）。

`.env.production` 当前是 `true`（纯前端独立演示用，答辩兜底），**部署到真后端时必须改**。
改完的产物应该是这样的：

```bash
grep -rl "vcp_mock_extra_users\|chenshiyuan@example.edu" dist/   # 应当无输出
ls dist/assets/mock-*.js                                        # 应当「没有那个文件」
```

#### 2026-09-25 实测：两套口径的产物对照（同一台机器、同一个 vite 8.3.0）

| 产物 | mock **关**（真后端口径，部署用） | mock **开**（纯前端演示口径） |
|---|---|---|
| `mock-*.js` | **不存在** | 46.77 kB / gzip 14.91 kB |
| 入口 chunk `index-*.js` | **22.93 kB** / gzip 7.87 kB | 62.62 kB / gzip 23.73 kB |
| 入口 preload 的其它 chunk | 9 个，合计 42.73 kB | 1 个（`useApi` 0.84 kB） |
| `request-*.js` | **113.14 kB** / gzip 42.91 kB | 114.36 kB / gzip 43.55 kB |
| `echarts-*.js`（懒加载） | 652.78 kB / gzip 219.43 kB | 652.78 kB / gzip 219.43 kB |
| `index-*.css` | 28.68 kB / gzip 6.17 kB | 28.68 kB / gzip 6.17 kB |
| `grep -rl vcp_mock_extra_users dist/` | 无输出 ✅ | 命中 `assets/mock-*.js` |

**两条容易误判的点**：

1. **入口 chunk 从 62.62 kB 掉到 22.93 kB，不是代码变少了** —— 是关掉 mock 后 rolldown 的分包策略变了：
   共享组件（`InkButton` 23.04 kB、`InkField` 10.48 kB、`pinia`、`InkDialog`…）被拆成独立 chunk
   并写进 `index.html` 的 `modulepreload` 列表。**看「首屏 JS 合计」才有意义**：
   mock 关 = 22.93 + 42.73 = **65.66 kB**（gzip 26.31 kB）；mock 开 = 62.62 + 0.84 = 63.46 kB。
   历史文档里「主 chunk ~57 kB」的说法来自更早的构建，随分包策略浮动，**别拿单个 chunk 做验收**。
2. **`echarts` chunk 不在 `index.html` 的 modulepreload 里**，只在打开图表页时才下载 ——
   所以那条「Some chunks are larger than 500 kB」警告说的是它，**不是主包**（`CLAUDE.md` 前端踩坑第 9 条）。

本次构建的 `dist/index.html`（真后端口径）入口引用如下，可直接与产物对照：

> **真后端口径**那一套（2026-09-25 构建，入口 `index-C47X2cye.js`），旧的 mock 产物已被覆盖。
> 要出纯前端演示包，删掉 `.env.production.local` 后重跑 `npm run build` 即可。


`dist/index.html` 里的引用是**根绝对路径**（`/assets/index-*.js`、`/favicon.ico`），
所以必须部署在域名根路径下。若要部署到子路径（如 `/vcp/`），得先在 `vite.config.js` 里设 `base: '/vcp/'` 重新构建。

## 六、Nginx

```bash
sudo cp deploy/nginx.conf /etc/nginx/conf.d/vcp.conf
# 【必改】server_name 与 root 两处
sudo nginx -t
sudo systemctl reload nginx
```

配置里逐条都写了注释，这里只重复三条**不写会出事**的：

| 配置 | 不写会怎样 | 实测情况 |
|---|---|---|
| `try_files $uri $uri/ /index.html;` | **刷新任何深层页面都 404**（history 路由的命门） | 2026-09-25 用本机替身实测：`/student/profile`、`/student/activities/389`、`/admin/colleges`、`/org/activities` 全部 200 且内容 = `index.html` |
| `location = /index.html` 的 `no-cache` | 发版后浏览器拿旧 index.html 请求已删除的旧 chunk → **白屏** | 替身实测 `/` 与深层路由都带 `Cache-Control: no-cache, must-revalidate`（`try_files` 的最后一个参数是 URI，nginx 会**内部重定向**并重新匹配 location，所以回退出来的 index.html 也会命中这一块） |
| `proxy_pass http://127.0.0.1:8080;`（**结尾不带斜杠**） | 带了斜杠会剥掉 `/api` 前缀，后端**一律 404** | 替身实测 `/api/v1/categories` 未登录返回 `{"code":20001,...}`（请求确实到了后端，路径没被剥） |

> ⚠️ **`/doc.html` 不经 Nginx**（2026-09-25 实测）：它不在 `/api/` 下，会落到 `location /`
> 被 `try_files` 回退成前端 `index.html`（替身实测 `GET /doc.html` → 200 + 前端页面，**不是** Knife4j 文档页）。
> 这是**有意为之**：prod 下文档页要求登录态，而浏览器打开文档页不会带 `Authorization` 头
> （Sa-Token 配的是 `is-read-header: true`、`is-read-cookie: false`），反代过去也只有 401 JSON，
> 没有可用性、反而多一处暴露面。要核「prod 收口是否生效」请**在服务器上直连后端**
> （见验收清单第 7 条）。确实需要经域名访问文档页时，`deploy/nginx.conf` 里留了注释掉的做法。

## 八、常见故障排查

| 现象 | 最可能的原因 |
|---|---|
| 页面能打开但**全是 mock 数字** | `.env.production` 的 `VITE_USE_MOCK` 没改成 `false`（坑 7） |

| 所有业务接口都返回 `{"code":20001,"message":"登录已过期"}` | 不是登录问题：后端没起或库连不上时也会是这个口径。先 `curl http://127.0.0.1:8080/api/v1/categories` 直连试一下 |
| 服务起来了，一登录就报数据库认证失败 | 凭证文件不在或口令写错（坑 3）；或口令被 YAML 当八进制解析了（坑 2） |

| `http://<域名>/doc.html` 打开的是前端页面（不是 Knife4j） | **正常现象**：文档页不经 Nginx（见第六节末）。要验 prod 收口请直连后端 |

| `/uploads/xxx` 图片 404 | `vcp.upload.dir` 与 `WorkingDirectory` 没对上，或图片没拷进 `/opt/vcp/uploads/`（第 4.2 节） |
