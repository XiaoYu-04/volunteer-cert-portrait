## 三、关键决策与理由

### 1. 纯手写组件，不引入 Element Plus

原型是一套**完整的设计系统**（零圆角、墨线分隔、印章式标签），与 Element Plus 的默认视觉冲突很大。
用 Element Plus 需要大量样式覆盖，且很难完全摆脱它的观感。手写组件虽然工作量大，但视觉一致性最好，
答辩时也讲得清"这部分是自己实现的"。

### 2. 保持 JavaScript，不迁 TypeScript

脚手架现成，省下的时间用于多铺页面。架构文档虽规划了 TS，但毕设答辩中 TS 并非必需项。

### 3. 用原生 CSS，不引入 Sass

原型本身就是纯 CSS，加 Sass 只会多一个构建依赖，没有实际收益。

### 4. 图表内的柱状元素保留轻微圆角

原型对柱状图用了 `borderRadius: [6,6,0,0]`，与页面 UI 的"零圆角"看似矛盾。
**这是原型的刻意选择**（页面 chrome 零圆角、图表内元素轻微圆角），已照搬并在代码注释与 README 中标注，不要"统一"掉。

### 5. Mock 分流：切换后端只改一个环境变量

后端未就绪，但不能把假数据散落在页面里。做法是 `api/*.js` 按真实契约书写，
由 `utils/request.js` 按 `VITE_USE_MOCK` 分流。后端就绪后改 `.env` 一个开关即可，页面代码零改动。

### 6. 状态枚举以后端为权威

本轮核对 `sql/02_schema.sql` 的列注释与 `sql/03_init_data.sql` 的 `sys_dict` 种子数据，
发现前端有 3 处码值对不上，**已按后端对齐**（后端脚本已在 PostgreSQL 18.6 实跑验证，是权威来源）：

| 字典类型 | 前端原值 | 已改为（后端值） |
|---|---|---|
| `attendance_status` | `UNSIGNED` | `NOT_SIGNED` |
| `notification_type` | `SYSTEM`/`ACTIVITY`/`AUDIT` | `SIGNUP`/`DURATION`/`SYSTEM` |
| `audit_action` | 缺 `SUBMIT` | 补上 `SUBMIT` |

顺带确认了两项**本来就一致、无需改动**的对接点：

- 认证头：后端 `sa-token.token-name: Authorization` + `token-prefix: Bearer`，与前端 `Authorization: Bearer <token>` 一致
- 路径前缀：后端未配 `context-path`，前端经 Vite 代理 `/api` → `8080`，到达后端即 `/api/v1/...`，与架构文档一致

### 7. 注册账号跨刷新持久化，其余实体保持内存态

mock 数据活在内存里，整页刷新会重置模块。注册产生的新账号如果不落盘，会出现
"注册 → 刷新 → 被踢回登录页，且新账号再也登不回来"。

只持久化**账号**这一项（`localStorage` 的 `vcp_mock_extra_users`）；其余实体（活动、报名、时长…）
保持内存态，刷新即回到干净的种子数据，方便反复演示同一条流程。想彻底重置清掉该 key 即可。
