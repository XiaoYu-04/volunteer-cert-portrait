## A. 需要先拍板（不定就无法开工）

- [ ] **A1 服务时长如何计算**
      是否取 `签退时间 - 签到时间`？是否受活动预计时长约束？异常签到的时长怎么算？
      → **阻塞 `vcp-certification` 的全部核心逻辑**

- [ ] **A2 签到/签退的时间窗口**
      活动开始前多久可签到？结束后多久必须签退？逾期是否自动记缺勤？
      → **阻塞 `vcp-volunteer` 的签到接口**

- [ ] **A3 报名人数上限的并发控制**
      `signed_count` 是冗余计数列，与报名明细可能漂移。测试项提到「活动已满继续报名」，
      但没说怎么防并发超卖。建议用行锁或 `UPDATE ... WHERE signed_count < max_count` 原子更新。

- [ ] **A4 审核驳回后如何重新提交**
      测试项提到该场景，但无状态机定义。

- [ ] **A5 `total_duration` 以哪张表为准**
      `student_info` 与 `student_profile` 各有一个同含义字段。**建议以 `student_info` 为准**，
      `student_profile` 仅作画像快照。

- [ ] **A6 时间类型是否改 `timestamptz`**
      现按原始设计用 `TIMESTAMP`（无时区）。单时区部署无影响，跨时区需改。

- [ ] **A7 逻辑删除与唯一约束的冲突**
      `activity_signup` 有 `uk_activity_student(activity_id, student_id)` 又有 `deleted` 软删除。
      若「取消报名」用软删除实现，同一学生再次报名会撞唯一约束。
      二选一：改成部分唯一索引 `UNIQUE (activity_id, student_id) WHERE deleted = 0`，
      或明确「取消 = 改 status、复用同一行」。

- [ ] **A8 演示数据尺度对齐（需与前端一起定）**
      前端 mock 的看板数字是 **86,420 小时 / 12,480 报名**，后端演示数据是 **156.2 小时 / 149 报名**，
      相差约 500 倍。接上真实接口时看板数字会暴跌，答辩时像是接口写错了。
      **建议放大后端演示数据去对齐前端**（前端已完成且有断言脚本，改动成本高；
      后端数据是生成的，放大只需改几个数字）。

## 推荐开工顺序

按《开发计划》的 P0 优先级（登录权限 → 活动报名 → 签到 → 时长审核 → 基础看板）：

```
B1 → B2 → B3 → B4 → B5        # 基础设施 + 登录打通，先证明这套架子能跑
  ↓
B6 vcp-system                  # 用户/角色/学生档案，后面所有模块都要用
  ↓
B7 vcp-org → B8 vcp-volunteer  # 组织 → 活动/报名/签到（B8 需要先定 A2、A3）
  ↓
B9 vcp-certification           # 时长认证（需要先定 A1）
  ↓
B10 vcp-portrait → B11 analytics → B12 联调
```

**A 组里最该先定的是 A1 和 A2** —— 它们分别卡住 `vcp-certification` 和
`vcp-volunteer` 的核心逻辑，而这两个模块是志愿服务闭环的关键。
其余 A 项可以在写到对应模块前再定。
