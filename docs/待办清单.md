- [x] 2026-09-23 **A1 服务时长如何计算**
      结论：`hours = (签退时间 − 签到时间) / 3600`，保留 2 位小数；**缺签退或签到状态为
      `ABNORMAL` 时取活动预计时长**；**上限为活动预计时长的 1.5 倍**（超出按 1.5 倍封顶）。
      理由：异常场景按预计时长计比按 0 计更贴近真实服务量，1.5 倍封顶则防止签到窗口被滥用。

- [x] 2026-09-23 **A2 签到/签退的时间窗口**
      结论：**活动开始前 30 分钟开放签到**；**活动结束后 30 分钟内必须签退**；
      未签退记 `ABSENT`，实现为**查询时惰性判定**（不引入定时任务，降低部署复杂度）。
      30 分钟为可调常量，集中定义在 `vcp-volunteer` 的常量类里。

- [x] 2026-09-23 **A3 报名人数上限的并发控制**
      结论：用 `UPDATE volunteer_activity SET signed_count = signed_count + 1
      WHERE id = ? AND signed_count < max_count` 原子更新，**影响行数为 0 即「已满」**。
      不做「先查再写」（存在 TOCTOU 窗口），也不用行锁（`volunteer_activity` 没有 `version` 列）。

- [x] 2026-09-23 **A4 审核驳回后如何重新提交**
      结论：`REJECTED` **允许重新提交**，回到 `PENDING_AUDIT`，
      并往 `duration_audit` 写一条新的 `SUBMIT` 流水（保留驳回历史，不覆盖）。

- [x] 2026-09-23 **A5 `total_duration` 以哪张表为准**
      结论：**以 `student_info.total_duration` 为准**，时长审核通过时由后端累加；
      `student_profile` 仅作画像快照，可随时由前者重算。

- [ ] **A6 时间类型是否改 `timestamptz`**

- [x] 2026-09-23 **A7 逻辑删除与唯一约束的冲突**

      **2026-09-23 进展：索引缺口已由 `sql/06_backend_gap_fix2.sql` 补 12 条并执行**

        全库也没有 `BEFORE UPDATE` 触发器；`04_demo_data.sql` 的三条回填 UPDATE 也从不写它。

      - 全库**零 CHECK、零触发器、零视图** → 状态机流转、时长非负、时间窗口全靠应用层守
      - **无乐观锁列**（无 `version`）→ MyBatis-Plus 的 `@Version` 用不了，
        A3 只能走行锁或 `UPDATE ... WHERE signed_count < max_count` 原子更新
