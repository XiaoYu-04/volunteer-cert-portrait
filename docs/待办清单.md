## A. 需要先拍板（不定就无法开工）

- [ ] **A1 服务时长如何计算**
      是否取 `签退时间 - 签到时间`？是否受活动预计时长约束？异常签到的时长怎么算？
      → **阻塞 `vcp-certification` 的全部核心逻辑**

- [ ] **A2 签到/签退的时间窗口**
      活动开始前多久可签到？结束后多久必须签退？逾期是否自动记缺勤？
      → **阻塞 `vcp-volunteer` 的签到接口**

- [ ] **A3 报名人数上限的并发控制**
      `signed_count` 是冗余计数列，与报名明细可能漂移。测试项提到「活动已满继续报名」，
      但没说怎么防并发超卖。建议用行锁或 `UPDATE ... WHERE signed_count < max_count` 原子更新。

- [ ] **A4 审核驳回后如何重新提交**
      测试项提到该场景，但无状态机定义。

- [ ] **A5 `total_duration` 以哪张表为准**
      `student_info` 与 `student_profile` 各有一个同含义字段。**建议以 `student_info` 为准**，
      `student_profile` 仅作画像快照。

- [ ] **A6 时间类型是否改 `timestamptz`**
      现按原始设计用 `TIMESTAMP`（无时区）。单时区部署无影响，跨时区需改。

- [ ] **A7 逻辑删除与唯一约束的冲突**
      `activity_signup` 有 `uk_activity_student(activity_id, student_id)` 又有 `deleted` 软删除。
      若「取消报名」用软删除实现，同一学生再次报名会撞唯一约束。
      二选一：改成部分唯一索引 `UNIQUE (activity_id, student_id) WHERE deleted = 0`，
      或明确「取消 = 改 status、复用同一行」。

- [ ] **A8 演示数据尺度对齐（需与前端一起定）**
      前端 mock 的看板数字是 **86,420 小时 / 12,480 报名**，后端演示数据是 **156.2 小时 / 149 报名**，
      相差约 500 倍。接上真实接口时看板数字会暴跌，答辩时像是接口写错了。
      **建议放大后端演示数据去对齐前端**（前端已完成且有断言脚本，改动成本高；
      后端数据是生成的，放大只需改几个数字）。

- [ ] **A9 `sys_user.status` 用什么类型**
      后端是 `1启用 / 0禁用`（数字标志位），前端是 `ACTIVE` / `DISABLED`（字符串枚举）。
      而且后端**没有** `user_status` 字典种子，与"状态一律走英文码 + `sys_dict`"的约定不一致。
      **建议后端改成英文码**，这样全项目的状态处理方式统一；否则前端的用户管理页要单独为这一个字段开特例。

- [ ] **A10 组织「停用/启用」是否保留**
      后端 `org_info.status` 只有 `PENDING`/`APPROVED`/`REJECTED`（审核状态），
      前端多做了"停用/启用"功能，接后端后会没有对应状态可用。
      **建议前端去掉** —— 资质审核本身已有"驳回"态，停用是额外引入的概念。

  > A9、A10 是前端与后端目前仅剩的两处**状态枚举**口径不一致，其余状态枚举前端已按后端对齐
  > （`attendance_status` 的 `NOT_SIGNED`、`notification_type` 的三值、`audit_action` 的 `SUBMIT`）。

- [ ] **A11 演示账号名不一致**（状态枚举之外的另一处口径）
      前端 / mock / 根 `README.md` 用的是 `org`，后端种子数据（`sql/03_init_data.sql`）是 `org_admin`。
      联调时照文档输入 `org` 会登录失败。二选一：前端与 mock 改成 `org_admin`，
      或后端种子改成 `org`（改后端只需动一行 SQL，但 `sql/README.md` §二 也要同步）。

### B-4 审计发现的既有缺口（写业务代码前先处理）

> 2026-09-22 用 4 路并行审计（工程现状 / 文档待办 / 前端接口反推 / 数据库闭环）交叉核对得出：
> 前端 28 个页面已经把字段契约写死，而 16 张表的列对不上，数据库层也有若干会影响实现的缺口。
> 这些不是"新功能"，是**写接口前必须先处理或明确绕开**的问题。

- [ ] **B16 前端要的字段，库里没有**（需扩表，或明确映射与 JOIN 方案）
      - 活动：`deadline`（报名截止）、`contact`（联系方式）**两列都不存在**
      - 报名：`reason`（报名理由）列不存在，但前端 `createSignup` 会提交它
      - 签到：`attendance_record` 没有 `activity_id`/`student_id`/`hours`，
        需经 `signup_id` 两次 JOIN 才能拼出前端表格要的字段
      - 时长：无 `proof`/`org_id`/`activity_type`；且 `signup_id` 是 NOT NULL UNIQUE
        而前端只给 `studentId` + `activityId`，**后端必须自己反查 `signup_id`**
      - 操作日志：`role`/`module`/`target`/`result` **四列全不存在**，
        而日志页 8 列都要，`module` 还是中文全等筛选（时长认证/志愿活动/活动报名/…）
      - 通知：`from`/`top` 两列不存在；且语义冲突 —— 表是「按收件人一行 + `is_read`」，
        前端既要"学校管理员发布公告"又要"学生看未读列表"，
        需决定公告是群发插行还是另建公告表
      - 组织：`college`/`member_count`/`founded_at`/`code` 都没有
      - 学生档案：`gender`/`grade` 没有；`phone` 在 `sys_user`、姓名在 `sys_user.real_name`
      - 分类：`activity_category` 没有 `code` 列，但前端 mock 里 6 个分类都有 code
      - 字典：前端要 `{dict_type: [{value, label, tone}]}` 的 **Map 形态 + tone 色调**，
        表是平铺行且**无 tone 列**，后端需 reshape（tone 可省略，前端缺省为 mute）
      - 权限：`RoleManageView` 要 `role.perms`（前端静态定义了 **28** 条权限标识：
        学生 5 / 组织管理员 7 / 学校管理员 16，已同步进 `StpInterfaceImpl`）与 `userCount`，
        **后端没有权限表、`sys_role` 没有 perms 列**

- [ ] **B17 数据库层缺口**（`sql/README.md` 之外的审计发现）
      - **`update_time` 永远不会自动刷新**：PostgreSQL 没有 `ON UPDATE CURRENT_TIMESTAMP`，
        全库也没有 `BEFORE UPDATE` 触发器；`04_demo_data.sql` 的三条回填 UPDATE 也从不写它。
        只能靠尚未实现的 `MetaObjectHandler`（B2）兜住，否则"最后修改时间"全部失真
      - 全库**零 CHECK、零触发器、零视图** → 状态机流转、时长非负、时间窗口全靠应用层守
      - **无乐观锁列**（无 `version`）→ MyBatis-Plus 的 `@Version` 用不了，
        A3 只能走行锁或 `UPDATE ... WHERE signed_count < max_count` 原子更新
      - **FK 列缺索引 7 处**（PostgreSQL 不为外键列自动建索引，与 MySQL 不同）：
        `duration_audit.duration_id`（已有 128 条流水）、`sys_user_role.role_id`、
        `org_info.contact_user_id`（还缺 UNIQUE）、`volunteer_activity.category_id` 等
      - **看板聚合所需索引缺口**：`attendance_record` 除唯一键外**无任何索引**，
        而 analytics 有 10 个接口要按签到时间聚合它；
        `notification(user_id, is_read)`、`activity_signup(signup_time)`、
        `service_duration(create_time)` 也未建
      - `org_info.org_name`、`activity_category.category_name` 无 UNIQUE；
        `volunteer_activity` 的 `category_id`/`org_id`/`start_time`/`end_time` 均可空

- [ ] **B18 公益等级/标签规则「已拍板但无处落库」**
      6 档阈值只硬编码在 `04_demo_data.sql:271-279` 的 `UPDATE ... CASE` 里，
      **无配置表、无字典类型**；`public_welfare_level` 直接存中文等级名，
      与「状态一律英文码 + `sys_dict` 翻译」的约定不一致。
      最脆弱的一处：**分类→标签映射以中文分类名为键**，而分类名可被
      `PUT /v1/categories/{id}` 改名 → 改名即静默丢标签，DB 层无任何保护。
      在 B10 落地时需确定单一事实来源（方案文档与 SQL 的 CASE 目前是两处重复定义）。

- [ ] **B19 前端契约的隐性要求**（写接口时必须遵守，否则联调即报错）
      - **越权风险（最重要）**：前端把 `studentId` / `orgId` 当查询参数自己传，
        mock 里 `eq(undefined)` 直接放行返回全量。**后端必须以登录态为准、忽略前端传入的
        这两个参数**，否则任意学生可查他人报名与时长
      - **`pageSize` 前端会传 500**（`DurationSubmitView`），不能把上限卡在 100，
        否则"我的时长"汇总与"时长提交"候选名单会缺数据（前端靠全量取回自己算汇总）
      - **静态段路由必须优先匹配**：`/activities/org-overview`、`/portraits/me`、
        `/portraits/distribution`、`/durations/batch-audit`
      - **错误码语义已固化**：`20001` 未登录/过期、`20002` 账号停用 ——
        前端命中即清 token 并跳登录，不要复用这两个码做别的错误
      - `unreadOnly` 可能是布尔 `true` 或字符串 `'true'`；空字符串筛选参数必须忽略
      - **`@OperationLog` 的 `module()` 必须用前端 `LogView.vue` 里写死的中文筛选项**：
        `时长认证 / 志愿活动 / 活动报名 / 用户与权限 / 签到签退 / 志愿组织 / 认证` ——
        前端是中文全等匹配，写错不报错但永远筛不出来。另外切面发出的 `OperationLogEvent`
        里 `username` 通常为空（登录会话只存 roleCode/orgId/studentId），
        **vcp-system 侧的落库监听器需按 `userId` 反查 `sys_user.username` 回填**

## 推荐开工顺序

按《开发计划》的 P0 优先级（登录权限 → 活动报名 → 签到 → 时长审核 → 基础看板）：

```
B1 → B2 → B3 → B4 → B5        # 基础设施 + 登录打通，先证明这套架子能跑
  ↓
B6 vcp-system                  # 用户/角色/学生档案，后面所有模块都要用
  ↓
B7 vcp-org → B8 vcp-volunteer  # 组织 → 活动/报名/签到（B8 需要先定 A2、A3）
  ↓
B9 vcp-certification           # 时长认证（需要先定 A1）
  ↓
B10 vcp-portrait → B11 analytics → B12 联调
```

**A 组里最该先定的是 A1 和 A2** —— 它们分别卡住 `vcp-certification` 和
`vcp-volunteer` 的核心逻辑，而这两个模块是志愿服务闭环的关键。
其余 A 项可以在写到对应模块前再定。

**前端（C 组）不在这条链路里** —— 它已完成且可独立运行，`C1`/`C2` 只是等 `A9`/`A10`
拍板后做两处对齐，`C3`–`C12` 都是收尾与可选功能。也就是说，**当前项目的瓶颈完全在后端**。
